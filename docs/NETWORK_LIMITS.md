# Anonymous network allowance

Implemented locally and in the AWS infrastructure templates on 27 September 2026. No AWS resources were deployed for this change.

## Behavior

The game allows three accepted questions per browser session per Bangkok calendar day, plus three shared by a network address that day. The API reports the smaller remaining allowance. A new incognito session on the same network sees the used network allowance. Existing reading history stays private to its original browser session. Invalid submissions do not consume slots; cancellation does not refund them. Infrastructure failures refund the original browser and network counters exactly once. Retries with the same request ID do not consume another slot.

IPv4 addresses are normalized, including IPv4-mapped IPv6. Native IPv6 uses a /64 prefix so switching temporary interface addresses does not reset the allowance. Equivalent IPv6 spellings produce the same result. IPv4 and IPv6 are separate networks; VPNs, changing networks/prefixes or switching address families can still obtain a separate allowance. Shared households, workplaces and carrier NATs can share a limit. The owner accepted these tradeoffs in preference to sign-in. This is not a reliable machine/person identity and does not use MAC addresses or browser fingerprinting.

## Trusted address and storage

1. On `/api/*`, a CloudFront viewer-request function replaces `x-blue-veil-network` with `event.viewer.ip`, discarding any viewer-supplied duplicate values. The managed AllViewerExceptHostHeader policy forwards it to the uncached API. The existing IAM Function URL and OAC restrict the origin to the configured distribution. Direct unsigned origin requests remain forbidden. Do not expose a second unprotected route to this handler.
2. Lambda accepts only this header, never `X-Forwarded-For`, `Forwarded`, the body, or the CloudFront origin connection address. The local loopback adapter instead uses the TCP socket address and ignores all forwarding headers. Missing or malformed addresses fail closed for session/allowance creation and question acceptance.
3. A 64-character random server secret produces HMAC-SHA256 over a version tag, Bangkok date and normalized network. Only the digest/day key and count/expiry reach DynamoDB. Including the day prevents ordinary database comparisons from linking a network across days. This is pseudonymization, not reversible encryption or a guarantee of anonymity; an operator with the secret and candidate IPs could recompute identifiers. Plain unsalted IP hashes would be guessable and are not used.
4. The network counter participates in the same transaction as the browser quota, reading/content, lock, idempotency and global acceptance counters. Conflicting transactions retry and re-check the cap. Reading ownership and random browser credentials never derive from the network digest.
5. Counters expire at midnight after the next Bangkok day (at most 48 hours). Scheduled cleanup removes expired records in batches; DynamoDB TTL is a delayed fallback, not an immediate-deletion guarantee. A temporary digest reference on unfinished reading metadata supports refunds; completion, cancellation or expired-content cleanup removes it. If content TTL deletion precedes cleanup, an abandoned reference can remain until the reading metadata's seven-day expiry and delayed TTL deletion. Ordinary reading/session retention remains as documented. Cloud service stream/backup retention is separate from deleting a live row.

The two DynamoDB tables already enable AWS-managed KMS encryption at rest. HTTPS protects the request path. The new HMAC key is encrypted in Secrets Manager, generated by CloudFormation without a plaintext source/config value, and readable only by the API workload role. Lambda environment contains its ARN, never the key value. The worker can refund network counters but cannot read the HMAC secret. Application logs, responses, queues and model prompts contain neither raw network addresses nor daily digests. WAF request sampling and CloudFront access logging are not enabled by this template; do not later enable raw request logging without a separate retention/privacy review.

Sources: [CloudFront viewer address and header structure](https://docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/functions-event-structure.html), [managed origin policies](https://docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/using-managed-origin-request-policies.html), [DynamoDB encryption](https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/encryption.howitworks.html).

## Key lifecycle and local development

The API caches the key in memory. Retrieval failures are not permanently cached and never fall back to an unkeyed hash or disabled network check. Retain this secret through deployments. Do not replace or rotate it mid-day: mixed old/new keys can split a quota. Rotation requires a coordinated maintenance window at the Bangkok day boundary and recycling all API execution environments; emergency compromise response may necessarily reset network counts. Global spend controls remain independent.

Local development creates a separate random key beside `LOCAL_STATE_FILE`, with the suffix `.network-key`, and reuses it across restarts. The default is under ignored `.private/`; the suffix is also ignored globally. Never print, commit or reuse that development key in AWS. This local file relies on filesystem permissions and is not a production secrets vault. Existing local question data is development data, not a claim of application-level encrypted local storage.

`LOCAL_NETWORK_QUOTA=off` is available only in the loopback local sample server for independent UI fixtures. It is ignored in local Bedrock mode and never read by the AWS adapter. Automated security tests exercise shared IPs, concurrency and spoofing with the network check enabled. Previously accepted questions without an address record cannot be retroactively counted against a network.

One Secrets Manager secret adds approximately $0.40/month plus retrieval charges at the published standard price, with retrievals cached per Lambda execution environment. Confirm the selected region's rates before deployment. [AWS pricing](https://aws.amazon.com/secrets-manager/pricing/).

## AWS release checks still required

- Resolve the existing deployment-region gate before any deployment.
- Verify the viewer function overwrites forged single/multi-value headers and that only the protected distribution can invoke the origin.
- Send concurrent synthetic submissions from several independent cookie jars; exactly three may succeed for one network/day, with no cross-session content access.
- Verify secrets fail closed, least-privilege grants, encrypted tables, log redaction and expired-counter cleanup in the deployed account.
- Verify midnight reset, cancellation, duplicate submissions, delayed workers and one-time refunds on real DynamoDB transactions. Local tests and synthesized templates do not prove these live integrations.
